# AI W-Guard 유속 서비스 (flow_service)

RTSP 영상을 직접 받아 **수면이 흘러가는 속도와 방향**을 격자 칸마다 계산하고, 그 결과를 TCP(JSON Lines)로
VMS에 보내는 프로그램입니다. 운영 중인 침수 감지 엔진(`ai_w_guard`)과는 **완전히 별개**로 돌아갑니다 —
이 프로그램을 켜고 끄거나 이 프로그램이 멈춰도 침수 감지에는 아무 영향이 없습니다.

- 원본(이 폴더): VMS 저장소 `flow_service/`
- 배포 위치: 추론 서버 `soldia-server@192.168.30.90:/home/soldia-server/aiwguard_flow`
- 기본 포트: **7200** (ai_w_guard 는 7100)

## 왜 별도 프로그램인가

AI W-Guard 가 보내는 물 폴리곤은 "물 영역의 테두리"뿐이라 유속 정보가 없습니다. 유속은 연속된 영상 프레임
사이에서 수면 무늬가 얼마나 움직였는지(광류)로만 알 수 있습니다. 이 계산을 침수 감지 엔진 안에 넣는 대신
별도 프로그램으로 두어, 운영 중인 엔진을 수정·재시작하지 않고 따로 켜고 끌 수 있게 했습니다.

## 동작 방식

1. 채널마다 FFmpeg 으로 RTSP 를 **15fps** 흑백 640px 폭으로 디코딩합니다(GPU `-hwaccel cuda`, 안 되면 자동으로 소프트웨어).
2. 초당 3번, 연속 3프레임(f0, f1, f2)으로 Farneback 광류를 3번 계산합니다: f0→f1, f1→f0(되돌리기), f0→f2.
3. 16×9 격자 칸마다 이동량의 중앙값과 두 가지 신뢰도를 구합니다.
   - `fb`: 앞으로 구한 이동을 거꾸로 되돌렸을 때 1px 안에 돌아오는 픽셀 비율(0~1)
   - `r`: 간격을 2배로 늘렸을 때 속도 ÷ 1배 속도. 실제로 떠내려가는 무늬면 1 근처, 제자리에서 출렁이는
     물결이나 맑은 물 아래 바닥 무늬면 0.5 근처가 됩니다.
4. 최근 3초 표본의 중앙값을 1초마다 VMS 로 보냅니다. 메시지 형식은 VMS `docs/PROTOCOL.md` 의 "유속 서비스 메시지".

15fps 를 쓰는 이유: 5fps 간격으로는 수면 무늬가 그 사이에 모양이 바뀌어 속도가 34~74% 낮게 나왔습니다(2026-09-21 실측).

## 설치 / 실행 / 중지 (추론 서버에서)

```bash
cd ~/aiwguard_flow
./start.sh      # 백그라운드 실행. 처음이면 .venv 생성 + opencv/numpy 설치, flow.cfg 가 없으면 예시에서 복사
./stop.sh       # 정상 종료 (FFmpeg 자식 프로세스까지 정리)
./run.sh        # 터미널에서 직접 실행(Ctrl+C 종료) — 문제 확인용
tail -f flow_service.log   # 로그 (5MB x 3개 순환). STATUS_LOG_INTERVAL_SEC 마다 채널별 fps/표본/계산시간 출력
```

필요한 것: Python 3.8+ (`python3-venv`), `ffmpeg`/`ffprobe`. OpenCV 와 numpy 는 `.venv` 안에만 설치되어
시스템 Python 이나 ai_w_guard, webconfig 에 영향을 주지 않습니다.

**재부팅 후 자동 실행**은 아직 설정하지 않았습니다. 필요하면 `aiwguard-flow.service` 안의 안내대로 systemd 에
등록하세요(관리자 권한 필요).

## 설정 (flow.cfg)

`flow.cfg.example` 을 복사해 씁니다(`start.sh` 가 없으면 자동 복사). 형식은 ai_w_guard 의 config.cfg 와 같습니다.
바꾼 뒤에는 `./stop.sh && ./start.sh` 로 다시 시작하세요.

| 항목 | 기본 | 설명 |
|---|---|---|
| `SERVER_BIND` / `SERVER_PORT` | 0.0.0.0 / 7200 | VMS 가 접속할 주소 |
| `DECODE_FPS` | 15 | 디코딩 FPS. 15 이상 권장 |
| `HWACCEL` | cuda | `cuda` 또는 `none` |
| `PROC_WIDTH` | 640 | 광류 계산 해상도(가로) |
| `GRID_COLS` / `GRID_ROWS` | 16 / 9 | 결과 격자 |
| `SAMPLES_PER_SEC` | 3 | 채널당 초당 표본 수. 표본 1개 = 광류 3회(약 70ms씩)라 4 정도가 한계 |
| `WINDOW_SEC` | 3 | 이 시간 동안의 표본 중앙값으로 내보냄 |
| `RTSP_URLn` / `RTSP_TITLEn` | 3, 4번 | **n 이 VMS 로 보내는 카메라 번호**. ai_w_guard 의 config.cfg 와 같은 번호를 쓰세요 |

## VMS 연결

1. VMS 설정 > **TCP 연결**에서 새 소스 추가: 모드 "접속", IP `192.168.30.90`, Port `7200`, 라벨 예) "유속 서비스".
2. 그 행의 **번호 기준**을 AI W-Guard 소스로 지정합니다. 유속 서비스는 AI W-Guard 와 같은 채널 번호를 보내므로
   이것만으로 같은 채널(예: 하천3, 하천4)에 붙습니다.
3. 설정 > 채널/RTSP 의 "실시간 수신 현황"에 `유속 cam 3 → 하천3` 처럼 초록색으로 보이면 연결된 것입니다.
4. 해당 채널에 ROI 를 그리면 ROI 마다 "유속 50px/s (51/52칸) ↗" 가 표시됩니다. 화살표 표시는 설정 > 알람 설정 >
   "유속 화살표를 화면에 표시"로 켜고 끕니다.

## 한계 (중요)

- 이 서비스가 보내는 값은 **화면상 속도**(정규화 좌표/초)입니다. 비스듬한 카메라는 같은 물살도 화면 위쪽(먼 곳)이
  느려 보입니다(실측: 같은 하천 근경 50px/s, 원경 11px/s). **실제 m/s 는 VMS 가 채널 "유속보정"(수면 기준점 4~8개)으로
  칸마다 환산합니다(VMS v0.3.2~)** — 이 서비스 쪽에는 보정 설정이 없습니다.
- 표면 유속이며, 유량 산정용 평균 유속과는 다릅니다(보통 표면 유속 × 0.85 안팎).
- 측정이 잘 되는 장면: 수면에 떠내려가는 무늬(물결·거품)가 보이는 곳. 잘 안 되는 장면: 폭포처럼 떨어지는 물,
  맑고 얕아 바닥이 비치는 곳, 제자리 정상파만 있는 곳(2026-09-21 cam1/cam2 에서 확인). 이런 칸은 `r` 이 낮아 VMS 가
  "믿을 수 있는 칸"에서 뺍니다.
- 야간(적외선), 강한 반사, 비가 오는 수면은 검증하지 않았습니다.
- 카메라 한 대에 RTSP 연결이 하나 더 붙습니다(VMS 영상 + ai_w_guard + 유속 서비스). 실제 CCTV 의 동시 접속 한도를 확인하세요.

## 문제 해결

| 증상 | 확인 |
|---|---|
| VMS 상태등이 "끊김" | `ss -ltn \| grep 7200` 으로 대기 중인지, `flow_service.log` 에 오류가 있는지 |
| `state` 가 계속 `connecting` | 로그의 `[CH n] 연결 실패` — RTSP 주소/카메라/네트워크 확인 (`ffprobe -rtsp_transport tcp <URL>`) |
| `GPU 디코딩 실패 -> 소프트웨어 디코딩` | 정상 동작하지만 CPU 사용이 늘어납니다. `HWACCEL = none` 으로 고정해도 됩니다 |
| 로그에 `밀려서 버림` 이 많음 | 계산이 표본 속도를 못 따라감 — `SAMPLES_PER_SEC` 을 낮추세요 |
| VMS 에 "매핑된 채널 없음" | TCP 소스의 "번호 기준"이 AI W-Guard 로 지정됐는지, 채널의 cam ID 가 번호와 같은지 |
